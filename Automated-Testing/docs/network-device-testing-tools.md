# 多设备网络功能测试工具选型指南

## 1. 文档目的

在交换机、路由器、防火墙和白盒网络设备的功能测试中，测试环境通常由多台被测设备、辅助设备、流量发生器、串口服务器和电源控制设备组成。测试过程不仅需要验证单台设备功能，还需要完成拓扑初始化、配置下发、协议收敛、流量验证、故障注入、日志采集和环境恢复。

本文介绍适合多设备组网测试的常用工具，并给出一套以开源软件为主、可逐步扩展的落地方案。

## 2. 典型测试目标

多设备网络测试通常覆盖以下内容：

- 二层功能：VLAN、Trunk、STP、LACP、MAC 学习、端口隔离和环路保护。
- 三层功能：静态路由、OSPF、IS-IS、BGP、ECMP、VRF 和策略路由。
- 数据中心网络：MLAG、EVPN、VXLAN、BGP Unnumbered 和 Overlay/Underlay 联动。
- 安全与策略：ACL、NAT、QoS、限速、认证和控制平面保护。
- 高可用性：链路倒换、设备重启、主备切换、协议重收敛和配置恢复。
- 数据面验证：报文转发、字段改写、丢包率、吞吐量、时延和抖动。
- 运维能力：配置保存、版本升级、日志、告警、Telemetry、SNMP 和 NETCONF/RESTCONF。

## 3. 工具分类与对比

### 3.1 拓扑与虚拟实验室

| 工具 | 主要用途 | 优点 | 局限 | 推荐场景 |
| --- | --- | --- | --- | --- |
| containerlab | 使用容器或虚拟 NOS 快速创建网络拓扑 | 拓扑即代码、启动快、便于接入 CI | 依赖厂商镜像，部分硬件特性无法模拟 | 路由协议、EVPN/VXLAN、配置回归测试 |
| EVE-NG | 运行路由器、防火墙等虚拟设备镜像 | 多厂商支持较好，图形化拓扑直观 | 资源消耗较大，镜像授权需要单独处理 | 综合网络实验室、售前验证、故障复现 |
| GNS3 | 图形化网络仿真与虚拟设备互联 | 易于上手，生态成熟 | 大规模自动化能力通常弱于 containerlab | 中小规模实验、教学和协议验证 |

如果测试重点是自动化回归，优先考虑 containerlab；如果设备类型复杂、需要运行传统虚拟机镜像，优先考虑 EVE-NG。

### 3.2 设备配置与状态采集

| 工具 | 主要用途 | 特点 | 适用情况 |
| --- | --- | --- | --- |
| Nornir | Python 网络自动化编排 | 原生支持并发、库存和任务插件，适合嵌入测试代码 | 多厂商真实设备的批量操作 |
| Netmiko | 通过 SSH 操作网络设备 CLI | 上手简单，支持大量厂商平台 | 仍需自行解析部分命令输出 |
| NAPALM | 提供统一的多厂商配置和状态接口 | API 一致性较好，适合读取通用状态 | 不同厂商驱动的能力覆盖并不完全一致 |
| Ansible | 声明式配置与批量任务执行 | 模块和社区资源丰富，便于运维人员使用 | 复杂测试状态机用 Playbook 表达时可能较笨重 |
| Scrapli | SSH/NETCONF 设备连接与命令执行 | 性能较好，异步支持完善 | 生态规模相对 Netmiko 较小 |

对于需要在测试逻辑中灵活控制多台设备的场景，推荐使用 Nornir 负责设备清单和并发调度，并根据设备类型选择 Netmiko、Scrapli 或 NAPALM 作为连接驱动。

### 3.3 自动化测试框架

| 工具 | 主要用途 | 优点 | 推荐场景 |
| --- | --- | --- | --- |
| pytest | Python 自动化测试框架 | 生态成熟、夹具灵活、参数化方便、容易接入 CI | 多厂商测试平台和自研自动化框架 |
| Robot Framework | 关键字驱动测试 | 测试步骤易读，适合测试人员协作 | 希望用较少代码描述业务测试步骤的团队 |
| pyATS/Genie | 网络设备测试与 CLI 解析 | Cisco 生态能力强，支持状态学习和差异比较 | 以 Cisco 设备为主的网络 |

通用多厂商环境建议选择 pytest。以 Cisco 为主且大量依赖 CLI 状态解析时，可以重点评估 pyATS/Genie。

### 3.4 流量生成与数据面验证

| 工具 | 类型 | 能力 | 适用场景 |
| --- | --- | --- | --- |
| TRex | 开源软件流量发生器 | 支持有状态和无状态流量，可生成较高性能流量 | 吞吐、丢包、NAT、防火墙和协议规模测试 |
| PTF | Python 数据面测试框架 | 可按端口收发报文并断言报文字段 | SONiC、白盒交换机和转发行为验证 |
| Scapy | 报文构造与解析库 | 构造协议报文灵活，适合异常和边界报文 | 协议功能、健壮性和低速精细报文测试 |
| Ostinato | 图形化或 API 驱动流量生成 | 使用方便，适合构造多种协议流 | 中小规模功能测试 |
| iperf3 | TCP/UDP 性能测试 | 部署简单，结果直观 | 端到端带宽、抖动和丢包验证 |
| Keysight Ixia | 商用测试仪 | 高精度、多端口、线速和标准测试套件 | 认证级性能测试、大规模协议仿真 |
| Spirent TestCenter | 商用测试仪 | 高精度性能与协议测试能力 | 运营商、数据中心和网络设备准入测试 |

开源方案可从 Scapy、iperf3 或 TRex 起步。若测试结果用于正式认证、招标指标或硬件规格验收，建议使用 Ixia 或 Spirent 等专业测试仪。

### 3.5 配置分析与资源管理

| 工具 | 主要用途 | 使用价值 |
| --- | --- | --- |
| Batfish | 离线分析网络配置、路径和策略 | 在设备启动前检查可达性、ACL、路由策略和配置变更影响 |
| NetBox | 管理设备、接口、地址、机柜、线路和租户 | 可作为测试实验室的资源与拓扑数据源 |
| Jenkins/GitLab CI/GitHub Actions | 自动触发并执行测试 | 支持定时回归、版本触发、报告归档和结果通知 |
| Allure | 测试报告展示 | 可展示步骤、附件、失败原因、趋势和历史结果 |

## 4. 场景化选型建议

### 4.1 多厂商真实设备功能测试

推荐组合：

```text
pytest + Nornir + Netmiko/Scrapli + Scapy/TRex + Allure
```

适合交换机、路由器和防火墙组成的物理测试床。Nornir 管理设备清单和并发操作，Netmiko 或 Scrapli 执行 CLI，pytest 编排用例，Scapy 或 TRex 负责流量验证，Allure 生成报告。

### 4.2 Cisco 为主的设备测试

推荐组合：

```text
pyATS + Genie + pytest/AEtest + TRex 或专业测试仪
```

该方案适合大量依赖 Cisco CLI 解析、协议状态学习和测试前后差异比较的环境。

### 4.3 虚拟拓扑与持续回归

推荐组合：

```text
containerlab + pytest + Nornir + GitLab CI/Jenkins
```

拓扑和设备启动参数保存为代码，每次提交后自动创建实验环境、执行测试并销毁环境，适合协议回归和配置模板验证。

### 4.4 SONiC 与白盒交换机测试

推荐组合：

```text
pytest + PTF + Ansible/Nornir + TRex
```

PTF 用于精确验证物理端口之间的报文转发和字段变化，TRex 用于较高负载下的转发性能测试。

### 4.5 认证级性能测试

推荐组合：

```text
pytest/Robot Framework + Ixia 或 Spirent + 实验室资源管理系统
```

适用于 RFC 2544、RFC 2889、吞吐、时延、丢包、协议规模和长时间稳定性等需要可重复、可审计结果的测试。

## 5. 推荐的开源工具栈

对于从零建设的多设备网络功能测试环境，建议第一阶段采用以下组合：

```text
设备与拓扑清单：YAML，后续可接入 NetBox
测试框架：      pytest
并发编排：      Nornir
设备连接：      Netmiko 或 Scrapli
状态解析：      TextFSM、TTP 或厂商 API
报文测试：      Scapy、iperf3
高性能流量：    TRex
测试报告：      Allure 或 pytest-html
持续集成：      Jenkins 或 GitLab CI
```

选择这套工具栈的原因：

- 对多厂商设备友好，不与单一厂商平台强绑定。
- 以 Python 为核心，测试逻辑、设备操作和流量控制可以使用同一语言。
- 可从少量设备逐步扩展，无需第一阶段就建设复杂平台。
- pytest、Nornir 和 Netmiko 社区成熟，问题排查和二次开发成本相对较低。
- 可以对接真实设备、虚拟设备和商业测试仪。

## 6. 建议的平台架构

```text
                      +------------------------+
                      | Jenkins / GitLab CI    |
                      | 定时、版本或人工触发   |
                      +-----------+------------+
                                  |
                                  v
                      +------------------------+
                      | pytest 测试编排层      |
                      | 参数化、夹具、断言     |
                      +-----+-------------+----+
                            |             |
                控制面操作  |             | 数据面验证
                            v             v
              +-------------------+   +-------------------+
              | Nornir            |   | Scapy/TRex/PTF    |
              | Netmiko/Scrapli   |   | Ixia/Spirent API  |
              +---------+---------+   +---------+---------+
                        |                       |
                        v                       v
              +-------------------+   +-------------------+
              | DUT 与辅助设备   |---| 流量端口/测试主机 |
              +-------------------+   +-------------------+
                        |
                        v
              +-------------------+
              | 日志、抓包、报告  |
              | Allure/日志平台   |
              +-------------------+
```

设备清单可以先使用 YAML 保存。规模扩大后，再由 NetBox 提供设备、接口、IP 地址和线缆关系，并增加测试床预约和资源锁定能力。

## 7. 典型自动化测试流程

以三台路由器组成的 OSPF/BGP 网络为例：

1. 申请并锁定测试床，避免多个任务同时使用相同设备和端口。
2. 检查设备管理地址、串口服务器、流量发生器和电源控制设备是否在线。
3. 备份当前配置，并将设备恢复到指定基线版本和基线配置。
4. 根据拓扑模板批量下发接口、路由协议和测试策略配置。
5. 检查物理接口、聚合接口和协议邻居状态。
6. 等待路由收敛，验证路由表、下一跳、ECMP 数量和策略结果。
7. 启动测试流量，检查连通性、丢包率、吞吐量、时延和报文字段。
8. 执行故障注入，例如关闭链路、重启进程、重启设备或切换主备节点。
9. 测量协议收敛和业务恢复时间，并验证备用路径是否符合预期。
10. 恢复链路和设备状态，再次检查控制面与数据面。
11. 收集设备日志、核心文件、配置、命令输出、抓包和测试仪结果。
12. 生成测试报告，并恢复实验室初始状态、释放测试资源。

## 8. 测试平台需要重点处理的问题

### 8.1 并发与超时

- 多台设备的配置和状态采集应并发执行，避免用例耗时随设备数量线性增长。
- 针对连接、命令、协议收敛和流量稳定分别设置超时。
- 不要只使用固定等待时间，应轮询目标状态并设置最大等待时间。

### 8.2 状态判断

- 尽量将 CLI 输出解析为结构化数据后再断言。
- 区分瞬态失败、环境失败、产品缺陷和测试脚本缺陷。
- 对邻居数量、路由数量、接口状态和丢包率等指标定义明确阈值。

### 8.3 环境恢复

- 每个测试套件都应具备清理逻辑，即使用例中途失败也能执行。
- 测试前保存配置检查点，测试后恢复基线配置。
- 对无法登录的设备准备串口和 PDU 重启通道。

### 8.4 资源与拓扑管理

- 记录设备、端口、线缆、流量仪端口和管理地址的对应关系。
- 增加测试床预约或资源锁，防止并发任务互相修改设备。
- 测试报告中应保存实际使用的拓扑、设备版本和配置版本。

### 8.5 可追溯性

- 保存测试脚本版本、拓扑版本、设备软件版本和执行参数。
- 失败时自动附加关键命令输出、系统日志和流量抓包。
- 对性能数据保留历史趋势，便于识别长期回退。

## 9. 分阶段落地建议

### 第一阶段：建立最小可用测试框架

- 使用 YAML 定义设备和接口。
- 使用 pytest 管理用例与断言。
- 使用 Nornir 和 Netmiko 完成批量配置及状态采集。
- 使用 ping、iperf3 和 Scapy 完成基础数据面验证。
- 在本地生成 JUnit、HTML 或 Allure 报告。

目标是先跑通少量核心用例，并保证失败时能够自动收集现场和恢复环境。

### 第二阶段：扩大覆盖范围

- 接入 TRex 或现有商业测试仪。
- 建立统一的 CLI/API 状态解析层。
- 增加链路中断、进程重启、设备重启等故障注入能力。
- 将测试接入 Jenkins 或 GitLab CI，执行每日回归和版本回归。

### 第三阶段：建设实验室管理能力

- 使用 NetBox 或自研服务管理设备、线路和拓扑。
- 增加测试床预约、资源锁定、使用记录和权限控制。
- 接入串口服务器、PDU、软件版本管理和自动装机能力。
- 建立结果趋势、失败分类和质量看板。

## 10. 选型检查清单

正式确定方案前，建议确认以下问题：

- 被测设备是真实硬件、虚拟设备，还是两者混合？
- 涉及哪些厂商、操作系统和软件版本？
- 设备支持 CLI、NETCONF、RESTCONF、gNMI 或厂商 API 中的哪些接口？
- 主要验证功能、性能、稳定性，还是协议一致性？
- 是否要求线速、多端口同步或纳秒级时延精度？
- 是否已有 Ixia、Spirent、串口服务器或 PDU 等实验室设备？
- 测试规模是固定拓扑，还是需要动态组合测试床？
- 是否需要每日回归、版本准入和长期趋势分析？
- 测试结果是否需要用于认证、招标或正式验收？
- 团队更熟悉 Python、Robot Framework，还是 Ansible？

## 11. 结论

多设备网络功能测试不存在覆盖所有需求的单一工具。更可行的方式是将测试框架、设备自动化、流量生成、拓扑管理和持续集成组合起来。

对于大多数多厂商功能测试项目，可以从以下方案起步：

```text
pytest + Nornir + Netmiko/Scrapli + Scapy/iperf3 + Allure
```

当测试规模或性能要求提高后，再逐步加入 TRex、containerlab、NetBox、CI 平台以及 Ixia/Spirent。这样既能控制初期投入，也能保留后续扩展空间。
